# i18n runtime

`src/modules/i18n` implements runtime localization for `kk`, `ru`, and `en` without adding a second language model. Locale values come from `src/shared/contracts.js`, where business aliases normalize as `KZ -> kk`, `RU -> ru`, and `EN -> en`.

## Runtime behavior

- `translate(namespace, key, locale, variables)` resolves exact locale, then `ru`, then the stable key.
- `resolveRequestLocale(headers)` reads `Accept-Language` including aliases and `q` values.
- `renderMessageTemplate(templateCode, locale, variables)` uses the same fallback chain for trigger templates.
- `renderTriggeredMessageTemplate({ templateCode, customer, eventPayload, variables })` selects the communication locale automatically from `customer.preferred_locale`, then `eventPayload.preferred_locale`, then `ru`.
- `/api/v1/i18n?locale=kk|ru|en` returns admin UI and Wallet dictionaries used by `public/app.js`.

## Customer 360

- `/api/v1/me/profile` uses `Accept-Language` for localized labels and messages.
- `Customer.preferred_locale` remains the saved communication preference and is returned as a canonical `Locale`.
- `PATCH /api/v1/me/profile` saves `preferred_locale` after alias normalization and rejects unsupported values with localized validation errors.
- Wallet labels in the profile response use the saved `Customer.preferred_locale`, so card language stays aligned with customer communication language.

No Loyalty, Transaction, Catalog, or Marketing domain structures are changed. Message-template localization is implemented as reusable runtime resources and helpers only at the language-selection boundary.
